**Date:** 2026-08-27 · **Target:** Sherwin Group EMCCD spectrometer control GUI
**Last commit:** 2018-08-23 (`167605b`) · 156 commits spanning 2015–2018
**Scope:** dependencies, outdated APIs, correctness, efficiency. Windows is the

## Summary

The code is a competent 2015–2018 PyQt instrument GUI that has aged in three
distinct ways, and it is worth separating them because they carry very different
risk.

First, an incomplete **Python 2 → 3 migration**. The `2to3` commit (`4485374`,
Sept 2017) fixed syntax but not semantics. Two consequences survive in the tree
today: cosmic-ray rebinning that raises `TypeError`, and a GPIB resource list
built as `bytes` that causes the software to silently and permanently fall back
to *fake* instruments. The second of these is the single most consequential
finding in this audit, because it fails quietly.

Second, **API rot**. `cosmics_hsg.py` uses three NumPy names that no longer
exist. This is latent — pinned dependencies hold it together — but it is what
makes the environment un-upgradable.

Third, **leftover development scaffolding in production paths**. The FVB
cosmic-ray routine opens three pyqtgraph debug windows every time it runs, with
no flag guarding it. The per-frame camera readout copies 640,000 pixels through
a Python list. Neither is subtle once you look; both have simply never been
looked at.

Underneath all three sits a threading model where worker threads touch Qt
widgets directly. The code contains a long comment describing a plot-freeze bug
that "doesn't seem to appear on faster-running computers." That is the signature
of a race condition, and the races are identifiable.

## Dependency & runtime landscape

**Two undeclared sibling dependencies.** `InstsAndQt` (repo:
`InstrumentLibrary-yolo`) and `hsganalysis` (repo: `HSG-turbo`) are resolved
only via `PYTHONPATH`. No pin, no vendoring, no submodule, no version recorded
anywhere. This is the largest single point of failure for reproducing the
environment — the app cannot start without them and nothing in the repo says
which revision it expects.

**pyqtgraph is pinned to 0.11.1** (2020, EOL). It uses `np.float` / `np.int`,
removed in NumPy 1.24, which `__main__.py:10-13` restores by monkeypatching the
NumPy namespace at import. The patch works, but it is a global mutation applied
before anything else loads, and it locks the pin in place.

**Generated UI files are stale.** All carry `PyQt5 UI code generator 5.6` (2016).
`UIs/Alignment_ui.py` is still *PyQt4*-generated (4.11.4) and was hand-edited to
import PyQt5 — so regenerating it from `Alignment.ui` would undo the edit.
`UIs/HSGFVB.ui` has no generated `_ui.py` at all.

**Build tooling is per-machine and dead.** `UIs/pyuic4` hardcodes
`/Users/Home/anaconda/lib/python2.7/site-packages/PyQt4/uic/pyuic.py`.
`MakeUI - Azul.bat` and `MakeUI - 1380D.bat` are leftovers from specific lab
machines.

**Hardcoded absolute paths.** `Z:\~HSG\Data\2018` (`__main__.py:400`) as the
default save directory — note the hardcoded *year* — and
`C:\Program Files\Andor SDK` (`Andor.py:434`) as the DLL fallback location.

## Correctness findings

### B1 — Single-image cosmic-ray removal is dead on modern NumPy · **Broken**

`cosmics_hsg.py:115` calls `np.cast['bool'](...)`, removed in NumPy 2.0.
Constructing a `cosmicsimage` raises `AttributeError` immediately.

Additional removed names in the same module:

| Name | Removed in | Sites |
|---|---|---|
| `np.cast` | 2.0 | `115`, `435`, `761` |
| `np.Inf` | 2.0 | 16 sites incl. `225`, `230`, `246`, `318`, `339` |
| `np.alen` | 1.23 | `249`, `252`, `342`, `345` |

Reached via `EMCCD_image.cosmic_ray_removal()` (`image_spec_for_gui.py:481`) →
`cosmics.cosmicsimage(...)` — the "Do CRR" path for single images. *Executed and
confirmed.*

### B2 — `rebin2x2` Python 2→3 division regression, same code path · **Broken**

`cosmics_hsg.py:836` passes `inshape/2` into `rebin`. Under Python 2 that was
floor division on an int array; under Python 3 it is a **float** array. `rebin`
then builds a reshape by string concatenation and `eval`s it (`:825`), which
raises:

```
TypeError: 'numpy.float64' object cannot be interpreted as an integer
```

Called from `lacosmiciteration` (`:508`), the main L.A.Cosmic loop. *Executed and
confirmed.* This is **independent of B1** — both must be resolved for that path
to work at all, so fixing the NumPy names alone would not restore it.

**This is not a NumPy-version issue.** The float array comes from Python 3 true
division, which `np.array([400,1600])/2` performs on *every* NumPy release
running under Python 3 — there is no older version on which it behaves
differently. Unlike B1, this failure is therefore **already live on the lab
Windows PC**, and has been since the 2017 migration. Single-image cosmic-ray
removal does not currently work there.

### B3 — GPIB auto-selection silently always falls back to "Fake" · **Broken**

`__main__.py:310`:

```python
ar = [i.encode('ascii') for i in rm.list_resources()]
ar.append('Fake')
s['GPIBlist'] = ar
```

Under Python 2, `.encode('ascii')` on a `str` returned a `str`. Under Python 3 it
returns **`bytes`**. The list therefore holds
`[b'ASRL6::INSTR', b'GPIB0::5::INSTR', ..., 'Fake']`, and the lookups that follow
compare `bytes` to `str`:

```python
idx = s['GPIBlist'].index('ASRL6::INSTR')     # always ValueError
idx = s['GPIBlist'].index('GPIB0::5::INSTR')  # always ValueError
```

Both raise `ValueError` unconditionally and fall through to the *Fake* index. The
spectrometer and the Agilent are therefore **never auto-connected**, and the
combo box renders its entries as `b'GPIB0::5::INSTR'`.

Introduced by the 2017 `2to3` migration (`4485374`). Not NumPy-dependent, not
platform-dependent — this has been the behavior on the lab PC for nine years.
*Simulated and confirmed.*

### L1 — `closeEvent` can close the window mid-exposure · **Latent**

`__main__.py:2094-2096` returns early when an exposure thread is running, without
calling `event.ignore()`:

```python
if self.getCurExp().thDoExposure.isRunning():
    log.info("Waiting for image collection to finish")
    self.sigUpdateStatusBar.emit("Please wait for exposure to complete")
    return                      # <- no event.ignore()
```

`QCloseEvent` is accepted by default, so the window closes anyway and the app
tears down during an active acquisition. Every sibling guard in the same method
*does* call `event.ignore()` — this one is the outlier, which reads as an
oversight rather than intent.

### L2 — Mutable default arguments, actively mutated · **Latent**

`EMCCD_image.__init__` (`image_spec_for_gui.py:352`) takes `raw_array=[]` and
`equipment_dict={}`, then line `388` writes into it:

```python
self.equipment_dict["background_file"] = ''
```

That mutates the **shared** default dict. Any two images constructed without an
explicit equipment dict share state. `HSG_FVB_image` (`:809`) and `Abs_image`
(`:1000`) repeat the same signature.

### L3 — Hardcoded 1600-pixel geometry · **Latent**

`gen_wavelengths` hardcodes `np.arange(-799.0, 801.0)` (`:1287`), and
`make_spectrum` hardcodes `.reshape(2,1600)` / `.reshape(3,1600)` at `:528`,
`:534`, `:939`, `:945`. Any horizontal binning or sub-ROI produces a shape
mismatch rather than a correct wavelength axis. The camera's own
`_getImageDims()` computes the real width — it just isn't consulted here.

### L4 — Identity comparison against literals · **Latent**

`__main__.py:61` — `if os.name is not "posix":`
`__main__.py:2147` — `if self.ui.tabWidget.indexOf(self.oscWidget) is not -1:`

Both emit `SyntaxWarning` on import today and work only because CPython interns
small ints and short strings. The `-1` case guards oscilloscope-tab teardown
during shutdown.

### L5 — `scipy.ndimage.filters` deprecated namespace · **Latent**

8 call sites in `cosmics_hsg.py`, plus `image_spec_for_gui.py:830` — which is on
the **live** FVB path, not the dead one. Warns on SciPy 1.13.

### S1 — Type checks miss NumPy scalars · **Smell**

`if type(other) in (int, float)` at `image_spec_for_gui.py:422` and `:453`
excludes `np.int64` / `np.float64`, so adding a NumPy scalar to an image silently
takes the array-addition branch instead. There is also an unreachable
`log.error(...)` immediately after a `raise` at `:428`.

### S2 — Ambiguous timestamps in every saved data file · **Smell**

`genEquipmentDict` (`ExpWidgs.py:847`) writes:

```python
s["date"] = time.strftime('%x %X%p')     # -> '08/27/26 14:14:56PM'
```

Two-digit year, locale-dependent field order, and a spurious `PM` appended to a
24-hour clock. This string is stamped into the JSON header of every image and
spectrum file — i.e. into the whole multi-year data archive.

## Threading — the likely root of the "unfindable" freeze

Worker threads mutate Qt widgets directly in several places, while the
surrounding code goes to real trouble to marshal through `sigMakeGui` and
`updateElementSig`. It is the inconsistency, not the model, that is the problem.

`takeContinuousLoop` (`ExpWidgs.py:638`) runs on `thDoExposure` and calls
`toggleUIElements()`, `view.removeItem(...)` and `setTabEnabled(...)` inline.
`processImageSequence` calls `updateSignalImage(d)` (`:1144`) and
`groupBox_37.setTitle(...)` the same way; `AbsWid` repeats it at `:2053`.
`genEquipmentDict` reads roughly fifteen widgets from the worker thread.

This is worth reading against the comment already in the source at
`ExpWidgs.py:612-628`, which describes plots freezing until the window is
resized, and notes the bug "doesn't seem to appear on faster-running computers
(better ram? faster cpu? details unclear)." Timing-dependent, machine-speed-
dependent, resolved by forcing a repaint — that is a race on the GUI thread, and
the calls above are candidates for it.

The sweep loops compound it. `doTHzPowerSweep`, `hwpSweepLoop` and `sweepLoop`
(`__main__.py:1414`, `1484`, `1626`) synchronize with `time.sleep()` followed by
`thread.wait()` polling, and drive the interface by emitting synthetic button
clicks (`ui.bCCDImage.clicked.emit(True)`) because calling the method directly
would touch widgets off-thread. The code's own comments concede "too many race
condition failures causing data collection to [fail]."

## Efficiency evaluation

### E1 — Per-frame camera readout: 35 ms/frame spent on a Python loop

`Andor.py:376-378` copies the ctypes buffer into a Python list one element at a
time, then reshapes the *list*:

```python
retnums = []
for i in range(x*y):
    retnums.append(retdata[i])
retnums = np.reshape(retnums, (y, x))
```

For a 1600 × 400 frame that is **640,000 interpreter iterations** per exposure.

| | Per frame |
|---|---|
| Current list-append loop | **34.7 ms** |
| `np.ctypeslib.as_array(...).reshape(y, x)` | **0.0007 ms** |
| Ratio | **≈ 53,000×** |
| Transient memory | ~18 MB of int objects vs. a 5 MB array |

Measured on this machine over 5 and 200 iterations respectively. This sits on the
path of **every** exposure, and continuous/alignment mode pays it per displayed
frame — which is precisely the mode where the freeze in the threading section
shows up.

### E2 — Three debug windows ship in the production cosmic-ray path

`HSG_FVB_image.cosmic_ray_removal` (`image_spec_for_gui.py:813-928`)
unconditionally constructs and `.show()`s **three** pyqtgraph
`GraphicsLayoutWidget`s — each with an `ImageItem`, a `HistogramLUTItem` and
plots — then keeps them alive on `self.winlist` (`:914`). There are also four
bare `print(d.shape)` calls.

Nothing guards any of it. The comparison is right there in the same codebase:
`ConsecutiveImageAnalyzer.removeCosmics` builds near-identical plots and
correctly gates all of them behind `if debug:`. The FVB routine was evidently
debugged and never un-instrumented.

### E3 — Per-pixel Python loop for cosmic replacement

Same method, `:918-926`. For each bad pixel it rebuilds a full index list
comprehension:

```python
for pix in badPixs:
    p = d[pix[0], [i for i in range(d.shape[1]) if not i==pix[1]]]
    d[pix[0], pix[1]] = np.mean(p)
```

O(n_bad × width) in pure Python. The `ConsecutiveImageAnalyzer` equivalent is
already fully vectorized with a boolean mask and `np.nanmean`; the FVB version
was never brought up to it.

### E4 — `gen_wavelengths` recomputed every frame

A ~20-term trigonometric expression evaluated over 1600 elements, re-run on every
`make_spectrum()` call — including once per frame in continuous mode — despite
depending only on `(center_lambda, grating)`, which change rarely.

### E5 — Full settings serialization on every acquisition

`takeImage` (`ExpWidgs.py:375`) calls `papa.saveSettings()`, which merges four
dictionaries and rewrites `Settings.txt` from scratch on each exposure.

It writes to the **current working directory**, not the data directory — and
`Andor.registerFunctions` performs an `os.chdir()` during startup
(`Andor.py:432-439`) to locate the SDK. The file's final location therefore
depends on import and failure order.

### E6 — Continuous mode allocates a full image object per frame

`ExpWidgs.py:645-650` constructs a complete `EMCCD_image` — an `np.array()` copy
of the raw frame plus a fresh `ConsecutiveImageAnalyzer` — purely to render the
live view, then discards it.

### E7 — Dead work per frame

`updateSignalImage` (`ExpWidgs.py:1475`) computes
`realPix = np.arange(start, stop, step)` and never uses it. The axis is set from
a lambda on the following line.

### E8 — Unbounded DEBUG logging across three files

`TheLog.log`, `TheCameraLog.log` and `TheInstrumentLog.log` are all plain
`logging.FileHandler` in append mode at `DEBUG`, with no rotation and no size
cap. A single sitting accumulated ~175 KB / 2,071 lines here. `Andor` sends
`DEBUG` to file while its `StreamHandler` sits at `WARNING`, and
`fakeAndor.myCallable.__call__` logs *every* DLL call. Handlers are attached at
module import (`addHandler` twice each in `Andor.py` and `__main__.py`), so any
re-import duplicates them.

### E9 — `eval()`-built reshape

`cosmics_hsg.rebin` (`:816-825`) assembles a reshape-and-sum expression by string
concatenation and `eval`s it, for what is a static operation. This is also what
turns the B2 type error into an opaque failure.

**Date:** 2026-08-28 · **Scope:** every claim in Part 7 of *The EMCCD Program: Complete
Reference* ("Hidden Behaviors and Known Bugs"), plus the bug-like claims Part 7 refers to
from elsewhere in the manual.

Part 7 is lab folklore — written from experience at the instrument, not from reading the
code. This addendum records which of it the source actually supports.

## A1 — Absorbance: the reference was never plotted · **Broken** · *fixed 2026-08-28*

`AbsWid.processImage` (`ExpWidgs.py:1900`) built the background-subtracted image,
computed the absorbance, and emitted the pair — then called
`super().processImage()`, which **rebuilds `curDataEMCCD` from `rawData`**
(`ExpWidgs.py:715`), discarding the subtraction, and emits that spectrum too. The
re-emitted array matches neither `id()` guard in `AbsWid.updateSpectrum`, so it fell to
the catch-all branch and overwrote `pRawTrans` — the curve holding the reference.

Net on screen: `pRawBlank` showed the image background-subtracted and `pRawTrans` showed
the same image un-subtracted. The reference was drawn for one frame and then clobbered.

Fixed by tracking whether an absorbance pair is currently displayed (`_absOnPlot`, set
per acquisition in `processImage` / `processImageSequence`, cleared when a new blank is
drawn) and skipping the catch-all redraw while it is. The no-reference path is unchanged.
Verified against both the pre-fix and post-fix code with a stubbed harness driving the
real `updateSpectrum`: the pre-fix code fails the re-emit case and the post-fix code
passes, with the no-reference, new-reference, and reference-reset cases identical in
both.

## A2 — Saved `abs_*` files have Blank and Trans columns swapped · **Broken** · *not fixed*

`Abs_image.__truediv__` (`image_spec_for_gui.py:1026`) is commented `# First is blank /
# other is transmission` and packs `(wavelengths, self, other, abs)`. Its only call site
is `curDataEMCCD / curRefEMCCD` — so `self` is the **image** and `other` is the
**blank**. The header written at `ExpWidgs.py:1990` reads
`Wavelength,Raw Blank,Raw Trans,Abs`, so both columns are mislabeled in every saved
absorbance file.

The absorbance column itself is correct: `-10·log10(image / reference)`.

This is worse than A1 — A1 was a display glitch, this is wrong metadata on archived data.
**Deliberately left unfixed:** correcting the order changes the layout of newly saved
files, and downstream analysis scripts may already compensate for the swap. Raise it with
whoever maintains those scripts first.

## A3 — Absorbance does not match its documented formula · **Broken** · *not fixed*

The manual states `Abs = −10·log((img − bg)/(ref − bg))`. On the single-image path the
reference is **not** background-subtracted — `processReference` (`ExpWidgs.py:2000`)
calls `make_spectrum()` on the raw frame, and only `processReferenceSequence` subtracts.
The live absorbance is therefore `(img − bg)/ref`. Which behavior is intended is a
physics question, not a code question.

## A4 — `enableCosmicRemovalDebug` is dead code · **Smell**

`confirmCosmicRemoval` (`ExpWidgs.py:1346`) implements a Shift-modifier cosmic-removal
review prompt gated on `enableCosmicRemovalDebug` (`ExpWidgs.py:135`), which is `False`
and never assigned anywhere. An undocumented modifier binding that cannot fire.

## A5 — Only the QWP/HWP sweep was hardened against the dropped-image race

`hwpSweepLoop` (`__main__.py:1560-1582`) now warns and waits another 0.5 s when
`thDoExposure` has not started, and reconciles progress against
`prevDataEMCCD.imageSequence.numImages()` rather than a local counter — its own comment
cites "too many race condition failures."

`sweepLoop` (`:1671`), `doTHzPowerSweep` (`:1457`) and `doConsecutiveLoop` (`:1736`)
still use the bare `clicked.emit()` → `time.sleep(0.2–0.5)` → `thDoExposure.wait()`
pattern. The manual describes this bug as universal; it is now specific to those three.
`doTHzPowerSweep` also confirms the manual's hardcoded `for ii in range(4)`.

Deliberately not ported: these loops cannot be exercised without the instrument, and a
wrong change here silently corrupts a sweep.

## A6 — The QWP pause hazard is identifiable · *needs the lab machine*

`checkPause` (`__main__.py:1517`) constructs a `QEventLoop` on the sweep worker thread,
then calls `connect` and `disconnect` on `hwpSweepProgress.pauseButton` — a widget owned
by the GUI thread — from that worker thread, and `exec_()`s the loop there. This is the
thread-affinity hazard the manual suspects, and it fits the reported pattern of working
on the office machine and failing on the lab machine.

One nearby red herring, ruled out: `StatusBarProgressHelper.setValue` (`__main__.py:163`)
passes a float to `QProgressBar.setValue`. On the pinned stack (PyQt5 5.15.11 /
Python 3.9) this emits a `DeprecationWarning` and works — *executed and confirmed* — so it
is not the crash. It will become a hard `TypeError` on a newer sip.

## A7 — Manual claims from outside Part 7, all confirmed

- Apply-button enable is a software-side flag pair (`changedSettingsFlags` /
  `changedImageFlags`, `__main__.py:1029`), never a camera query — as §2.2 warns.
- Exposure/gain change detection compares against the cached `CCD.cameraSettings` dict,
  not the camera (`ExpWidgs.py:398`) — as §3.2 warns.
- Wiregrid transmission is read from `motorDriverWid.ui.tCosCalc` inside a `try/except`
  that only logs (`ExpWidgs.py:903-914`). Silent on failure, exactly as §6.2 describes.
- `Slits` is shared through `papa.settings["slits"]` and pushed into each experiment
  widget on open (`__main__.py:820`) — the §3.4 caution is real.

## A8 — Part 7 omits the worst bug in the program

Finding B3 above — the GPIB list built as `bytes`, so instrument auto-selection silently
always fell through to *Fake* — is nowhere in the manual, which is consistent with a
failure that never announced itself. It is fixed in the working tree at
`__main__.py:330` (uncommitted). Single-image cosmic-ray removal (B1/B2) was also dead at
`167605b` and now runs — *executed and confirmed* end to end against
`cosmics_hsg.cosmicsimage`. Part 4.1 documents that feature as usable; on the committed
tree it was not.
